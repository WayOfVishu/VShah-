# PRD: Job Board Discovery & Resume Tailoring Pipeline

> **Revision note:** This draft has been through two LLM council review
> passes. Round 1 established the core architecture: gate resume tailoring
> behind an explicit user action instead of auto-firing it off discovery.
> Round 2 audited whether that fix was actually *enforced* by this document
> or just *described*. It found that two safeguards (no-fabrication,
> prompt-injection resistance) were prose instructions with no verification
> mechanism, that the invocation spike needed to be a hard blocking task
> instead of a footnote, and that uncapped discovery + mandatory per-row
> approval creates an un-triaged queue that risks becoming rubber-stamping.
> All of round 2's fixes are baked into this version — every safeguard
> below is written as a concrete mechanism (a threshold, a state machine, a
> retry count), not a description of intent.

## 1. Introduction/Overview

The user runs a manual job search tracked in an existing local dashboard
(`Job-Tracking-Dash`, Node/Express/better-sqlite3) that logs applications
*after* they're submitted. That dashboard has no way to *find* jobs — the
user still hand-browses job boards every day.

This feature adds a **discovery pipeline**: a manually-triggered tool that
pulls fresh postings from job sources, dedupes them, and writes them into a
new `discovered_jobs` table the user reviews in the dashboard. For postings
the user actually wants to pursue, they explicitly request a tailored
resume draft, generated by Claude Code from their base resume and that
posting's description. The user still does the actual applying by hand —
this tool's job ends at "here's a reviewed, tailored resume, ready for you
to submit."

**Design constraint driving this PRD:** LinkedIn's and Glassdoor's Terms of
Service prohibit automated access even when authenticated, and LinkedIn
actively detects and bans accounts for it. Because of that, this pipeline is
tiered by risk:

- **Tier 1 — Public APIs (no login, no ToS issue).** Greenhouse, Lever, and
  Ashby expose public JSON job-board endpoints per company. This tier does
  the heavy lifting.
- **Tier 2 — Public feeds/pages (no login, generally tolerated).**
  Remotive, RemoteOK, and WeWorkRemotely APIs/RSS, plus company career pages
  with `schema.org` `JobPosting` markup.
- **Tier 3 — Authenticated platforms (LinkedIn/Glassdoor/Wellfound).**
  Explicitly **out of scope for this PRD**, uncontested through two rounds
  of review. If ever built, it would be a separate, manual-triggered,
  low-volume Playwright + real-Chrome flow using a reused login session —
  never a scripted login, never run on a tight loop, never paired with
  fingerprint-spoofing or anti-detection tooling. This document does not
  cover its implementation.

**Goal:** every time the user runs the discovery command, every genuinely
new posting from zero-risk sources lands in the dashboard, deduplicated.
The user reviews the list at their own pace and requests a tailored resume
only for the postings they actually want to pursue — keeping both Claude
Code usage and review effort proportional to real interest, not to how many
postings happened to exist that day.

## 2. Goals

1. Surface **every** new job posting from Tier 1 + Tier 2 sources with zero
   authentication and zero ToS risk — discovery is free (SQLite rows, no
   LLM tokens), so there is no reason to cap it.
2. Spend Claude Code usage **only** on postings the user has explicitly
   selected, never automatically on every discovered posting — this is the
   real cost control, not a per-run count limit.
3. Eliminate duplicate postings (the same role cross-posted on multiple
   boards) before they reach the dashboard.
4. Generate a tailored resume draft, on request, for any discovered
   posting, using only content that already exists in the user's real
   resume — never fabricated experience or claims — and make that
   guarantee checkable, not just stated.
5. Extend the existing job-tracking dashboard rather than duplicate it —
   one SQLite file, one UI, a new "Discovered" view alongside the existing
   "Applied" log, with a clean reconciliation path between the two.
6. Keep the whole pipeline manually triggered — no unattended cron job
   hitting any external service, and no unattended LLM invocation with
   filesystem write access.
7. Keep the "Discovered" queue reviewable, not a wall of undifferentiated
   rows — uncapped discovery must not turn the approval gate into
   fatigue-driven rubber-stamping.

## 3. User Stories

- **As the user**, I want to run one command each morning and see every
  new posting from my configured sources, so I don't have to manually
  browse five different job boards.
- **As the user**, I want the same job posted on two different boards to
  show up once, not twice, so I don't waste review time on it.
- **As the user**, I want to pick which discovered postings are worth a
  tailored resume, and only pay Claude Code usage for those, so my usage
  scales with my actual interest, not with how many postings a source
  happened to publish that day.
- **As the user**, I want to see the exact prompt and posting content
  before Claude Code writes a resume file, so nothing gets written to disk
  without my review.
- **As the user**, I want any tailored-resume line that doesn't clearly
  trace back to my real resume flagged for me before I approve it, so I
  never accidentally submit a fabricated claim — and if I choose to approve
  it anyway, I want that decision recorded so I know later why it's there.
- **As the user**, I want to see discovered postings in the same dashboard
  where I already track applications, and have marking one "applied"
  reconcile cleanly with my existing log, so I have one place to work from.
- **As the user**, I want a source that repeatedly fails to render to tell
  me so clearly, instead of just quietly showing fewer postings.
- **As the user**, I want the tool to never touch my LinkedIn or Glassdoor
  login, so there's no risk of my accounts getting flagged or banned.

## 4. Functional Requirements

### Connectors
1. The system must fetch postings from Tier 1 sources (Greenhouse, Lever,
   Ashby) using each platform's public JSON board API — no browser, no
   login.
2. The system must fetch postings from Tier 2 sources (Remotive, RemoteOK,
   WeWorkRemotely) using their public APIs/RSS feeds.
3. The system must support fetching Tier 2 company career pages that expose
   `schema.org` `JobPosting` markup, rendering JS-driven pages via the
   Lightpanda headless browser (already cloned locally) where a plain HTTP
   fetch isn't enough to see the listings.
4. If a source connector runs but finds no `JobPosting` markup / no
   minimum threshold of extractable content, the system must **not**
   silently treat that as "no new postings." Each source tracks a
   `retry_count` in a `sources` (or `source_runs`) table: a render/fetch
   failure increments it and the source is retried on the next run. After
   **3 consecutive failures**, the source is marked
   `status = 'permanent-fail'` and surfaced as a **persistent dashboard
   warning** (not just a line in the terminal run summary) until the user
   investigates. A single transient failure is not alarming; three in a
   row is a source that's actually broken (career-page markup changed,
   API shape changed, anti-bot measures kicked in) and must not be
   mistaken for "nothing new today."
5. Tier 2 connectors must apply a **stated** rate limit — no more than one
   request per host every 2 seconds, with exponential backoff on HTTP 429
   — configured via a `rateLimitMs` field per source in
   `config/sources.json`, not left as an implicit "be polite" convention.
   Scraping being ToS-permitted does not mean unthrottled.
6. Each connector must be independently runnable and independently
   configurable, so a broken or rate-limited source doesn't block the
   others.
7. The system must read its source configuration (Tier 1 company
   watchlist, Tier 2 keyword list, rate limits) from a single local config
   file (`config/sources.json`), not hardcoded in connector code.
8. **Seed configuration must be derived from data the user already has, not
   invented:**
   - The Tier 1 seed watchlist must be generated by querying the existing
     `jobs` table (`Job-Tracking-Dash`'s `jobs.db`) for distinct companies
     the user has already applied to, then checking which of those have a
     public Greenhouse/Lever/Ashby board. This is a one-time bootstrap
     script, not a hand-typed list.
   - The Tier 2 keyword seed list must be derived from the distinct job
     titles already present in that same `jobs` table (normalized to
     keyword clusters), not guessed. If the existing `jobs` table has too
     few rows to derive a useful seed (fewer than ~5 distinct titles), fall
     back to a short, clearly-labeled placeholder list of 5-10 broad
     keywords for the user to edit — but the derived-from-real-data path is
     the default, not the guess. (This is a known v1 limitation: a
     brand-new tracker with few logged applications gets a thin starting
     config either way — see Open Questions.)
   - Both lists remain user-editable in `config/sources.json` after the
     bootstrap; this only sets the starting point.
   - A broader, scripted-enumeration watchlist (hundreds of companies via
     public Greenhouse/Lever/Ashby board directories) is explicitly
     deferred to a future version — disproportionate to this system's
     current review volume and adds no value until the triage/ranking in
     req. 20 is in place and proven.
9. Tier 3 platforms (LinkedIn, Glassdoor, Wellfound) must not be contacted
   by this system in any way.

### Normalization & Dedup
10. The system must normalize every fetched posting into one unified
    schema: `job_id, source, title, company, location, salary,
    description, apply_url, posted_date, remote_status`.
11. The system must fuzzy-match postings on normalized `title + company +
    location` to detect the same role cross-posted on multiple sources, and
    collapse matches into a single discovered-job record that lists every
    source it appeared on.
12. The system must not re-surface a posting (by dedup match or identical
    `apply_url`) that was already written to the database in a previous
    run.

### Run behavior — discovery is uncapped
13. The system must be triggered manually by the user running a single
    local command (e.g. `npm run discover`) — no OS-level scheduler
    (cron/Task Scheduler) is part of this system.
14. Discovery has **no per-source cap.** Every new, deduplicated posting
    found in a run is written to `discovered_jobs` with `status = 'new'`.
    Discovery costs no LLM tokens, so capping it only hides postings
    without saving anything real.
15. The system must print a run summary to the terminal: postings fetched
    per source, duplicates collapsed, new postings written, and any
    `render-failed` or `permanent-fail` sources (req. 4).
16. The system must include a simple retention step: `discovered_jobs` rows
    still in `status = 'new'` after 60 days must be auto-marked
    `status = 'archived'` (not deleted) so the active Discovered view
    doesn't accumulate stale postings indefinitely. Archived rows remain
    queryable/exportable but are hidden from the default dashboard view.

### Storage
17. The system must store discovered postings in the same SQLite database
    file used by the existing dashboard (`jobs.db`), in a new
    `discovered_jobs` table separate from the existing `jobs` (applied)
    table.
18. The `discovered_jobs` table must track at minimum: the unified schema
    fields (req. 10), `sources` (list of boards it was found on),
    `first_seen_at`, `status` (`new` / `queued` / `generating` /
    `tailored` / `rejected` / `dismissed` / `applied` / `archived`),
    `resume_path`, `match_score` (nullable real — no scoring logic ships in
    v1, but the column exists now so a future ranking feature is a
    backfill, not a migration), and `applied_job_id`: a nullable foreign
    key into the existing `jobs` table, declared `ON DELETE SET NULL` (if
    the linked applied-job row is ever deleted, the discovered-job record
    is preserved and simply unlinked — it is never cascade-deleted).
19. Source health (req. 4-5) must be tracked separately from individual
    postings — a `sources` table (or equivalent) keyed by source name,
    holding `retry_count`, `status` (`ok` / `render-failed` /
    `permanent-fail`), and `last_success_at`.

### Resume tailoring — gated on explicit user action, with a real state machine
20. Resume tailoring must **never** run automatically on newly discovered
    postings. It only runs for a `discovered_jobs` row the user has
    explicitly marked (e.g. checking it in the "Discovered" view and
    clicking "Tailor Selected," or passing its row ID(s) to a manual CLI
    command). Marking a row this way sets `status = 'queued'`. The
    Discovered view must sort by `match_score` (when populated) then
    recency, so uncapped discovery doesn't just become an unordered wall
    of rows the user has to triage by hand (req. 2 Goals).
21. Tailoring follows an explicit status transition, not an implicit one:
    `queued` → (user confirms, req. 21) → `generating` → `tailored` on
    success or back to `queued` with a visible error on failure (req. 24).
    From the Discovered view the user can also move a `queued` row to
    `rejected` (terminal — will not be re-offered for tailoring unless
    manually reset) or edit-and-re-queue it. This state machine, not just
    "there's a confirm button," is the actual approval gate.
22. Before invoking Claude Code (i.e. before the `queued → generating`
    transition), the system must show the user the constructed input (the
    posting's normalized description + the instructions Claude Code will
    receive) and require explicit confirmation. No file write happens
    without this confirmation. **This may not be the only gate:** the
    invocation spike (req. 26) must determine whether a non-interactive
    Claude Code call also triggers its own, separate filesystem-write
    permission prompt at the OS/tool level. If it does, the UI must surface
    that as a second, distinct confirmation rather than assuming the
    in-app "Confirm & Generate" click is the only checkpoint — this is not
    resolvable by design discussion, only by running the spike.
23. The tailoring instructions given to Claude Code must explicitly
    constrain it to reorder, reweight, and rephrase content that already
    exists in the user's base resume — never invent skills, experience,
    dates, or metrics not present in the source. This constraint is
    enforced by a concrete post-generation check, not left as a prompt-only
    promise:
    - After generation, the system runs a similarity/traceability check
      comparing each substantive line of the tailored draft against the
      base resume (e.g. token-overlap or embedding-similarity scoring —
      exact method is an implementation choice, see Open Questions).
    - Any line falling below the traceability threshold is flagged and
      shown to the user as part of the approval view (req. 22/6 Design
      Considerations) — not silently accepted, and not silently blocked
      either.
    - The user may approve a flagged line anyway (they know their own
      resume better than a heuristic does), but doing so requires typing
      or selecting a short reason, which is written to an `overrides`
      table (`discovered_job_id`, `flagged_text`, `reason`, `timestamp`).
      This is the audit trail: nothing gets silently rubber-stamped past a
      fabrication flag.
24. Scraped job-description text is untrusted input. Before it is
    interpolated into the tailoring prompt template, the system must strip
    or neutralize instruction-like patterns (e.g. phrases resembling "ignore
    previous instructions," "system:", embedded directives) and wrap the
    posting content in clear delimiters marking it as data to summarize,
    not instructions to follow. This must be covered by a test fixture — a
    fake posting containing an injection attempt — asserting the sanitizer
    catches it before the confirmation preview (req. 22) is ever shown.
25. The base resume must be a single, canonical Markdown file the user
    maintains at a fixed path (`resume/base-resume.md`). The traceability
    check (req. 23) always diffs against this one file — maintaining
    multiple resume versions is out of scope for v1 (see Open Questions).
26. Each tailored draft must be written as a new Markdown file (never
    overwriting the base resume), named to trace back to its posting (e.g.
    `resume/drafts/{company}-{title}-{job_id}.md`), and the discovered-job
    row's `resume_path` must be set, with `status` moving to `tailored`.
27. **Before building the invocation mechanism, the system must be spiked
    first, as a blocking task with a written go/no-go outcome** (see §7
    Technical Considerations) — not a design note, not folded into the
    tailoring build. The spike confirms, for this user's actual setup:
    (a) whether a non-interactive Claude Code invocation bills against the
    existing subscription session or requires a separately-billed API key,
    (b) whether it can hang on a filesystem-write permission prompt, and
    (c) whether it raises a second, tool-level confirmation beyond the
    in-app gate (feeds directly into req. 22). The result determines which
    mechanism is used:
    - **If the spike confirms safe non-interactive invocation:** the
      `queued → generating` transition (req. 21) shells out to Claude Code
      directly and captures its Markdown output to `resume/drafts/`.
    - **If it does not:** that transition instead writes the constructed
      prompt + posting content to a file for the user to paste into their
      own interactive Claude Code session, who then saves the result to
      the same `resume/drafts/` path themselves. This is not a lesser
      fallback — it's the same human-reviewed step either way, just with a
      manual paste instead of a scripted call.
28. If resume tailoring fails after being requested, the row must fall back
    from `generating` to `queued` with a visible error, not silently
    disappear or revert to `new` (req. 21).
29. The system must not perform any auto-apply action — output stops at a
    tailored resume draft; submitting the application is manual and outside
    this system.

### Dashboard
30. The existing dashboard's Express server must expose the discovered jobs
    through new endpoints (list, request-tailoring/confirm, reject, update
    status) without changing any existing `/api/jobs*` route or the
    existing `jobs` table.
31. The dashboard UI must gain a "Discovered" view listing discovered jobs
    sorted by `match_score` then recency (archived hidden by default),
    showing source(s), title, company, location, status, and a link to the
    tailored resume draft when present. Source health (req. 19) must be
    visible as a persistent banner/badge when any source is
    `permanent-fail` — not buried in a log.
32. From the "Discovered" view, the user must be able to: select one or
    more rows and request tailoring (req. 20-22); reject or dismiss a row;
    or mark a row `applied`, which creates the corresponding row in the
    existing applied-jobs log pre-filled from the discovered job's data and
    sets `discovered_jobs.applied_job_id` to link the two records (req. 18).

## 5. Non-Goals (Out of Scope)

- **No LinkedIn, Glassdoor, or Wellfound scraping of any kind.**
- **No stealth/anti-detection tooling** — no fingerprint spoofing, no
  human-like mouse/typing simulation, no stripping of automation-detection
  flags, no proxy rotation to dodge bans. Not in scope for any tier.
- **No auto-apply.** The system never submits an application.
- **No automatic resume tailoring.** Every tailoring run results from an
  explicit user selection and confirmation (req. 20-22) — a hard non-goal,
  not a v1 simplification to relax later.
- **No unverified fabrication/injection safeguards.** "The prompt says not
  to" is explicitly insufficient — both must have the concrete mechanisms
  in req. 23-24, or they don't count as done.
- **No OS-level scheduling.** The user runs the discovery command by hand;
  no cron job, Windows Task Scheduler entry, or background daemon.
- **No unthrottled scraping.** Tier 2 connectors carry a stated rate limit
  (req. 5) — "free to scrape" is not "unlimited requests."
- **No deep pagination / mass scraping.** Each source connector pulls a
  bounded, recent slice of postings — not a full historical crawl.
- **No scripted mass company-enumeration in v1** (req. 8) — the seed
  watchlist starts from the user's own application history, not a scraped
  directory of hundreds of companies.
- **No multi-version resume support in v1** (req. 25) — one canonical base
  resume file.
- **No new database engine.**
- **No mobile app or notifications (push/email/SMS).**

## 6. Design Considerations

- Extend the existing dashboard's look and structure (`public/index.html`,
  `style.css`, `app.js`) rather than building a separate UI — add a
  "Discovered" tab/section next to the current applied-jobs table.
- Visually distinguish every status in req. 18 so the user can tell at a
  glance what still needs a decision versus what's already actioned.
- The tailoring confirmation view (req. 22) must show, inline, both the
  constructed prompt/posting content **and** — once generation has run —
  any traceability-flagged lines (req. 23) highlighted directly against the
  base resume, not tucked away in a separate log file. If overriding a
  flag, the reason-entry field belongs in this same view.
- Source health warnings (req. 31) should be a persistent, dismiss-able
  banner, not something that only appears in a terminal run summary.

## 7. Technical Considerations

- **Task 1.0, before any pipeline code, is the invocation spike — a
  blocking task with a written go/no-go, not a design note.** Spike a
  non-interactive Claude Code invocation (`claude -p "..."` or equivalent)
  from a script, against one throwaway fake job posting, and record: (a)
  whether it bills against the existing Claude Code subscription session
  or requires a separately-billed API key, (b) whether it hangs on a
  filesystem-write permission prompt, and (c) whether it raises a *second*
  tool-level confirmation beyond whatever the app itself shows. Outcome
  (c) specifically decides whether req. 22's approval gate is one control
  or two — build the tailoring UI before this is known and it will be
  built for the wrong number of gates.
- **Stack consistency:** Node.js throughout, matching the existing
  dashboard (`better-sqlite3`, `express`), connectors as plain modules
  using `fetch` for Tier 1/2 API calls.
- **Lightpanda usage:** scoped strictly to Tier 2 pages that need JS
  rendering to expose `schema.org` `JobPosting` data. Driven via its CDP
  server (`lightpanda serve`) using a Playwright/Puppeteer CDP client —
  plain page-load-and-read, no interaction scripting. Must implement the
  fail-loud/retry/permanent-fail behavior in req. 4 rather than treating an
  empty render as "no postings." A fallback to a full Playwright+Chrome
  render for pages Lightpanda can't handle is a reasonable v1.5 addition
  once real render-failure rates are measured — not required for v1.
- **Dedup:** `fuse.js` for fuzzy matching on `title + company + location`,
  run before insert.
- **Traceability check (req. 23):** start with a cheap, deterministic
  heuristic (e.g. n-gram/token overlap between tailored lines and the base
  resume) rather than a second LLM call — an LLM-judged fabrication check
  adds cost and latency to the exact step this PRD is trying to keep cheap
  and fast. Revisit only if the heuristic's false-positive/false-negative
  rate proves unworkable in practice.
- **Prompt-injection sanitizer (req. 24):** implement as a small, testable
  pure function (strip/neutralize known instruction-like patterns, wrap
  posting text in explicit delimiters) with its own unit test using an
  injected-text fixture — not an inline step buried in the tailoring
  script.
- **Config file:** `config/sources.json` holds the Tier 1 company
  watchlist, Tier 2 keyword list, and per-source `rateLimitMs`,
  bootstrapped per req. 8, hand-edited thereafter — no admin UI needed for
  v1.

## 8. Success Metrics

- Running the discovery command produces, on a normal day, every genuinely
  new posting from active sources with duplicates already collapsed —
  nothing held back by an artificial per-source cap.
- Zero requests made to LinkedIn, Glassdoor, or Wellfound by this system,
  ever.
- Zero tailored resumes generated without an explicit user selection and
  confirmation — verifiable by `discovered_jobs.status` only reaching
  `tailored` via the `queued → generating → tailored` path, never directly
  from a discovery run.
- Every tailored resume draft's lines are either within the traceability
  threshold against the base resume, or explicitly overridden with a
  logged reason in `overrides` — never silently accepted below threshold.
- A source that fails 3 runs in a row is visibly flagged as
  `permanent-fail` in the dashboard, not just quietly producing fewer
  postings.
- The user can go from "run the discovery command" to "select a posting
  and get a reviewed, tailored resume" using only the terminal and the
  dashboard — no separate tool, no manual file hunting.

## 9. Open Questions

- **Invocation mechanism outcome, including the single-vs-double gate
  question — RESOLVED (2026-08-31), see `scripts/spike-claude-invoke.js`
  in this project (`Job-Board-Scraping`):**
  - **(a) Billing:** with no `ANTHROPIC_API_KEY` set, `claude -p "..."`
    still succeeded — it authenticates via the same logged-in Claude Code
    session (subscription) used interactively, not a separate billed API
    key.
  - **(b) Hang risk:** it does **not** hang on a filesystem-write
    permission prompt. Without `--allowedTools`, the `Write` call is
    auto-denied non-interactively and Claude reports that in its text
    reply, exiting cleanly (exit 0, no timeout).
  - **(c) Second gate:** none. No separate OS/tool-level confirmation
    dialog exists that could block a script — permission is resolved
    entirely by the `--allowedTools` (or
    `--allow-dangerously-skip-permissions`) flag passed at invocation
    time. Passing `--allowedTools "Write"` scoped to the invocation lets
    it write without any further prompt.
  - **Decision:** req. 22's approval gate is a **single control** — the
    in-app "Confirm & Generate" click. `tailorInvoke.js` shells out to
    `claude -p` directly (PRD req. 27's first branch) with
    `--allowedTools "Write"` and `--add-dir` scoped to `resume/drafts/`,
    capturing stdout for the run log. Task 5.5 (second-gate UI) is
    **not needed** and is skipped per its own instructions.
- **Traceability-check method and threshold (req. 23) — RESOLVED
  (2026-09-01), see `lib/traceabilityCheck.js`:**
  - **Method:** two independent deterministic rules, no LLM call (per §7).
    (1) *Token overlap* — unigram coverage of each tailored line against the
    base resume's token set, plus a bigram bonus rewarding intact phrasing,
    weighted 0.75/0.25. Tokens are suffix-stemmed so `pipeline`/`pipelines`
    and `trigger`/`triggering` count as the same evidence, while technical
    tokens (`node.js`, `ci/cd`, `k8s`, `100k+`) are left verbatim.
    (2) *Numeric support* — every number a line asserts must appear in the
    base resume. This exists because overlap alone is blind to the most
    likely real fabrication: a line made entirely of the resume's own words
    with one metric inflated. Measured, "40%" changed to "85%" scores 0.92
    on overlap and would have passed silently.
  - **Threshold: 0.55.** Tuned against the real base resume, not guessed:
    the resume scored against itself flags 0 of 67 lines (all score 1.0); a
    genuinely-rephrased draft scores 0.662-1.0 with 0 flags; five clearly
    fabricated lines score 0.0-0.335 and all 5 flag. 0.55 sits in the empty
    gap between those two clusters with margin on both sides.
  - **Known limitation:** the check scores vocabulary and numbers, not
    meaning. A fabrication reusing the resume's exact words and real numbers
    to assert something it doesn't say — moving a true achievement to a
    different employer, say — will pass. That is the accepted cost of the
    cheap-heuristic choice in §7; the user still reviews the draft, and §7's
    "revisit only if the false-positive/false-negative rate proves
    unworkable" still stands.
- **Bootstrap script for req. 8:** the exact query/logic to derive the seed
  watchlist and keywords from the existing `jobs` table needs to be
  written as part of implementation — this PRD specifies its inputs and
  fallback behavior, not the exact matching/normalization logic.
- **Cold-start scope:** if the user's existing `jobs` table has very few
  applications logged, the derived seed watchlist/keywords (req. 8) will
  be thin regardless of the placeholder fallback. This is acceptable for
  v1 — the config is user-editable — but worth flagging as a known rough
  edge rather than a fully solved problem.
- **`match_score` scoring logic:** the column exists (req. 18) but no
  scoring algorithm ships in v1. Whether/how to rank discovered postings
  against the user's outcome history in the existing `jobs` table is future
  work, not blocking for this PRD.
- **Tier 3 (LinkedIn/Glassdoor):** intentionally deferred — if the user
  wants it later, it should be scoped as its own, separate PRD given the
  materially different risk profile.
