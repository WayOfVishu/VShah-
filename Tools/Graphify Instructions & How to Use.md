## 1. You mostly don't invoke it

Three layers push the graph at every session automatically, in increasing force:

| Layer | File | What it does |
|---|---|---|
| Project instructions | `CLAUDE.md` | Loaded every session; tells Claude to query the graph before browsing source |
| Hook guards | `.claude/settings.json` | Intercepts every `Read` / `Glob` / `Bash` / `Grep` and injects a MANDATORY "query first" instruction — it also tells subagents to inherit the rule |
| Earned memory | `graphify-out/memory/` | Carries specific answers and dead ends forward (§5) |

So **"feeding the graph to the next session" is already wired up.** Just start a
session in this repo.

One requirement: pip's user script directory must be on `PATH`, or every hook
silently no-ops and you get no graph at all.

```
C:\Users\Vihang\AppData\Roaming\Python\Python312\Scripts
```

This was the original failure mode here — `graphify` was not installed, the hooks
had been firing and failing on every single tool call, and nothing surfaced an
error. If the graph ever seems ignored, check this first:

```bash
graphify --version      # command not found => PATH problem, not a graph problem
```

The read guard is **unconditional** — it fires even on `README.md`. If that gets
noisy, narrow the `Read|Glob` matcher in `.claude/settings.json`.

## 2. The one big gotcha: query matching is literal

`graphify query` matches via **case-folded substring + IDF**. There is
**no stemming, no synonyms, no cross-language matching.**

Query with **identifiers that exist in the code**, not prose:

```bash
graphify query "renderHeatmap discovered_jobs"    # good — real symbols
graphify query "how does scoring work"             # bad — substring-matches score/rank everywhere
```

The bad example above really did drag League-ML and Stocks nodes into a
Jobs-Web-App question. Prose queries fan out across every project in the monorepo.

If a question uses different vocabulary than the code, pull the graph's actual
vocabulary first and pick terms from it (full procedure in
`.claude/skills/graphify/references/query.md`).

```bash
graphify query "<question>" --budget 4000   # default 2000 truncates fast
graphify query "<question>" --dfs           # trace a chain, not a neighborhood
graphify query "<question>" --context call  # restrict to one edge type
```

## 3. Daily commands

```bash
graphify explain "renderHeatmap()"          # node + every edge, with file:line
graphify path "renderAll()" "dateKey()"     # shortest path between two symbols
graphify affected "DateWindow" --depth 2    # reverse: what breaks if I change this
graphify god-nodes --top 10                 # architectural hubs
```

`explain` and `affected` are the highest value-per-token of the set:

- **`explain`** answers "what is this and what touches it" in ~15 lines instead of
  reading a whole file.
- **`affected`** is a blast-radius check. Run it *before* a refactor.

In-session, `/graphify <question>` routes to the same machinery.

## 4. Updating

```bash
graphify update .                          # after code changes — incremental, AST-only, free
graphify extract . --code-only --force     # full rebuild after big refactors or deletions
```

Both cost **zero tokens** and need no API key. Run `update` after a refactor, not
after every save. `CLAUDE.md` already instructs Claude to run it after edits.

Gotcha: `update` prunes nodes from deleted files, but a rebuild that comes out
*smaller* than the existing graph is rejected unless you pass `--force`.

Regenerate derived views after a big change:

```bash
graphify export wiki      # 150 articles + index.md, the agent entry point
graphify export html      # graph.html, interactive
```

## 5. The memory loop — the real context carry-forward

The graph gives **structure**. This gives **conclusions**.

```bash
graphify save-result \
  --question "where is the heatmap rendered" \
  --answer   "renderHeatmap() at public/app.js:176, called by renderAll()" \
  --nodes    "renderHeatmap()" \
  --outcome  useful          # or: dead_end | corrected

graphify reflect             # digest memory/ -> reflections/LESSONS.md
```

`dead_end` and `corrected` are the valuable ones — they record where the graph
**misled** you, which is exactly what a fresh session would otherwise repeat.
`reflect` half-lifes old signal at 30 days and needs 2 corroborating results
before it prefers a node.

These two directories are **git-tracked on purpose** while the rest of
`graphify-out/` is ignored — they are knowledge earned by working in the repo,
not output derived from it, so they cannot be regenerated by a rebuild.

## 6. Currently degraded — both need an API key

The Claude CLI's OAuth login does **not** satisfy these. They need
`ANTHROPIC_API_KEY` (or `GEMINI_API_KEY` / `OPENAI_API_KEY`) in the environment.

| Gap | Effect | Fix |
|---|---|---|
| Communities unlabeled | Named after hub files (`public/app.js`) instead of real concepts | `graphify label .` |
| AST-only extraction | Calls / imports / definitions only; no inferred relationships | `graphify extract . --mode deep` |

The second is the bigger loss. AST edges tell you what calls what; semantic
extraction is what surfaces *"these two modules are coupled through a shared
assumption."* Worth a few dollars of API credit if you lean on this heavily.

Everything else works fully offline at zero cost.

## 7. Setting up a new machine

`graphify-out/` build output is gitignored, so a fresh clone has no graph:

```bash
py -m pip install --user "graphifyy[sql]"    # the [sql] extra parses .sql files
graphify extract . --code-only               # local AST, no API key, no token cost
graphify export wiki                         # optional, rebuilds the wiki
```

Then add the Scripts directory from §1 to `PATH` and restart the shell.

`.graphifyignore` is committed and defines the scope. It excludes:

- **`External Repos/`** — git submodules are *gitlinks*, so `.gitignore` does not
  cover them and graphify would walk straight into vendored upstream code.
- **`Virtual Environments/`** — 1.8 GB, the single largest directory in the repo
  by a factor of 23.
- **`References/`** — PDFs and scanned textbooks, not code.

Verified: zero excluded paths appear in `graph.json`.

## 8. What is tracked vs. ignored

| Path | Git | Why |
|---|---|---|
| `.graphifyignore` | tracked | Defines scope; the part worth sharing between machines |
| `graphify-out/memory/` | **tracked** | Earned knowledge, not reproducible |
| `graphify-out/reflections/` | **tracked** | Digest of the above |
| `graphify-out/graph.json` | ignored | ~2.7 MB, rewritten wholesale on every change |
| `graphify-out/graph.html` | ignored | ~2.2 MB, same |
| `graphify-out/wiki/` | ignored | Regenerated by `graphify export wiki` |

## 9. Maintenance warning

`graphify install --platform claude` rewrites `SKILL.md` and `references/` in the
skill directory, backing up the previous `SKILL.md` as `SKILL.md.bak`. This file
deliberately lives in `Tools/` rather than inside the skill directory so a skill
upgrade cannot touch it.

After upgrading the package, re-sync the project copy of the skill from the
global one:

```bash
py -m pip install --user --upgrade graphifyy
graphify install --platform claude                  # refreshes ~/.claude/skills/graphify
cp -r ~/.claude/skills/graphify/. .claude/skills/graphify/
rm -f .claude/skills/graphify/SKILL.md.bak
```

The project copy at `.claude/skills/graphify/` is the one that syncs between
machines; the global one at `~/.claude/skills/graphify/` is per-machine. A
version mismatch shows up as a warning on every `graphify` invocation.
